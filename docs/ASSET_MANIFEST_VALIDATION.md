# Canonical asset-manifest validation

This document covers the **metadata-only** generator `scripts/asset-manifest.mjs` used for host-owned astrological chart artwork. No asset images, textures, font binaries, production payloads or user data are stored in the chart package. This check does not establish redistribution rights.

## Ordering contract

Schema version 1 manifests emitted by `generate()` always sort their `files` entries by **literal relative `path`** using JavaScript ordinal string comparison (`a < b`), irrespective of selection order or directory traversal order. Each file contains `path`, `bytes` and `sha256`; the manifest fingerprint is the SHA-256 digest of `JSON.stringify(files)` in this exact order.

`validateManifest()` now enforces the generated order, in addition to validating the schema, supported literal asset paths, duplicate/case-insensitive collisions, byte counts, hexadecimal SHA-256 values and fingerprint.

A manifest with correctly recalculated hashes but shuffled file entries is rejected with `Manifest files must be in canonical path order`. Both `verify()` and `compare()` call this validator and reject such manifests rather than returning a misleading result or different diff ordering depending on the caller's input.

This does **not** mean that a manifest fingerprint is a signature. A caller with write access can create a new valid manifest. The filesystem bytes are checked against the provided SHA-256 values when `verify()` is called; signature-based authorization and redistribution approval are separate concerns.

## Local verification

Run from an isolated checkout of this branch:

```bash
npm ci
npm run test:asset-manifest
npm run test:assets
```

The new regression `rejects reordered manifest entries even with a recomputed fingerprint` checks:

- Selection permutations generate the identical canonical manifest.
- A valid canonical manifest is accepted.
- A shuffled manifest with an updated fingerprint is rejected.
- `verify()` and `compare()` reject the same shuffled manifest.

A green Node test suite does not certify visual parity across skins, browser/Three.js behavior, asset licensing or Astrolabio e-ink delivery.

## Compatibility and migration

Manifests generated by the existing `generate()` implementation already use this ordering, so their contents are unchanged. Consumers that construct manifest files manually or reserialize the `files` array in a different order must restore canonical order **and then recalculate the fingerprint** before verification. No schema version change, production asset path rename or package API change is introduced.

Keep this PR in draft until the local Node suite and any relevant downstream consumer checks have been executed and reviewed.
